## Corpus and independent labels

There are 102 files: 51 development and 51 holdout. Each split has 31 guitar chord voicings, 16 single notes, silence, broadband noise, percussive noise bursts, and one four-chord transition phrase. All pitches come from handwritten standard-tuning six-string fret charts or explicit string/fret single notes; labels are not read from any detector, chord dictionary, or analyzer feature dump. A theory-only interval assertion catches mislabeled charts.

Coverage includes open E2 through fretted C#6; repeated pitch classes at different octaves; all twelve pitch classes across the corpus; major/minor; dominant seventh, major seventh, minor seventh; sus2/sus4; add9; major/minor sixth; diminished and augmented triads; C/E and D/F# inversions; and power chords with no third. Holdout changes key using physical capos 1, 3, or 6, strum direction, excitation brightness, rate, strengths, detuning, and recording noise. Maximum single-note fret is 21; chord shapes are physically playable compact grips. Per-string attack times, MIDI pitches, string/fret, damping times, strength, and detuning are explicit in `manifest.json`.

The renderer uses a fractional-delay Karplus–Strong string loop excited with filtered deterministic noise, with pick attack, natural harmonic decay, independent string strengths, staggered strums, release damping, and optional low recording noise. This is actual PCM through the complete audio front end, not a supplied spectrum or ideal chroma vector. Transition releases overlap subsequent attacks by 300 ms. The `overlap_*` note metrics score the union of independently timed strings during that overlap; settled note/identity metrics exclude it. Identity is deliberately unscored there. The separate harmonic-boundary diagnostic uses nominal new-strum onsets even while the previous chord releases; it is not a claim of a unique identity throughout overlap. Per-string pitch means nearest equal-tempered MIDI, with cents also supplied; microtonal estimation is outside this score.

C6/Am7 and sus2/inverted sus4 have identical pitch-class interpretations; augmented triads have root symmetry. The manifest preserves intended names as provenance but marks root/quality as unknown for unique-identity scoring and provides acoustically equivalent candidate pairs. Suspended chords, sixths, and minor sevenths still receive pitch-set, bass, and compatible-identity scores. Thirdless power chords have no forced major/minor/root identity. Candidate sets are conservative within this corpus's vocabulary, not a claim that every chord has only those theoretical names.

## Holdout discipline

Use only `dev` while implementing or tuning. The historical adapter intentionally has no holdout switch. The independent tester should run holdout once on a frozen implementation, recording source revision, binary hash, configuration, machine, input inventory, and raw results. Builders may read the generator but should not inspect holdout predictions or tune against holdout failures. This is process isolation, not a secret benchmark: both splits are visible and the synthesis family is shared. Any repeated tuning against this holdout invalidates it; create a new independent version and report prior exposure. A second human-played holdout is required before real-guitar accuracy claims.

## Harness format and integration

`score.py` accepts a JSON array of predictions in a **validation-only exchange format**, not a proposed Rust API. `rust_eval.py` now implements the CLI and result contract published in `docs/rust-architecture.md`. It uses FFmpeg to independently decode WAVs to mono 24 kHz f32le, runs an existing local binary with bounded timeouts, preserves raw outputs, and adapts the union of the two observed note streams. Unknown harmony remains null identity; bass uses the independent bass estimate. `adapt(case, output)` retains its canonical union interface for the separate real-audio evaluator; it is not the strict wire validator. The Rust runner calls `validate_wire` first and never silently skips invalid output. `dom7`/`min7` map to harness `7`/`m7`. Other valid wire qualities remain valid wrong predictions on this corpus. This adapter and wire validation have not yet been exercised against an actual Rust binary. Each entry has exactly these fields:

```json
{
  "id": "dev_note_00",
  "duration": 2.0,
  "frames": [
    {"start": 0.0, "end": 2.0, "midis": [], "root": null, "quality": null, "bass": null}
  ]
}
```

`frames` are half-open nonoverlapping segments that tile the whole file, including explicit no-detection/unknown intervals. They may have arbitrary durations. `midis` is a unique list of sounding MIDI pitches; `root` and `bass` are independent integer pitch classes C=0 through B=11, or null. Quality is one of `maj`, `min`, `7`, `maj7`, `m7`, `sus2`, `sus4`, `add9`, `6`, `m6`, `dim`, `aug`, or null. The scorer also accepts the contract’s additional `madd9`, `add11`, `madd11`, `dim7`, `hdim7`, and `5` predictions, so an incorrect but valid quality is scored rather than crashing. No-chord means empty notes and null chord fields. Monophonic notes may have MIDI pitches while chord root/quality stay null. Bass should reflect actual lowest sounding voice, not an inferred root. The canonical format has no evidence field. The runner validates the original wire evidence: finite score/margin in 0..1 and the declared level enum, with no confidence cutoff or probability interpretation. Confidence calibration remains untested.

The scorer requires all and only the selected split's fixture IDs, rejects duplicates, nonfinite times, invalid types/pitches, and timeline gaps/overlap. Unknown outputs are explicit nulls, never quietly removed from denominators. Missing capabilities must be stated separately. An adapter must not manufacture a polyphonic set from a chord name, derive bass from root, or infer notes using the expected manifest. It may read fixture IDs, paths, durations and split to run files; its musical predictions must use only analyzer output. Preserve original raw output alongside adapted data.

After the builder produces the binary, run:

```sh
python3 validation/audio/rust_eval.py --binary target/release/analyze-pcm --split dev
# Optional focused auto-only dev run; default above exercises all three modes:
python3 validation/audio/rust_eval.py --binary target/release/analyze-pcm --split dev --modes auto
# Independent evaluator only, after source/configuration freeze:
python3 validation/audio/rust_eval.py --binary target/release/analyze-pcm --split holdout --allow-holdout
```

The runner defaults to separate `auto`, `monophonic`, and `polyphonic` dev exercises. Freeze the selected modes/configuration before any intentional holdout run; `--allow-holdout` is required by the CLI (and an explicit flag by Python callers). No holdout detector run was performed here.

Each invocation creates `results/rust-<split>/<UTC-time>-<unique-id>/run.json`, with a status and run ID. Per-mode subdirectories retain decoded PCM, raw JSON, canonical `predictions.json`, stdout/stderr for both processes, and (only on complete success) `score.json`. Always require `run.json.status == "succeeded"` and a matching score run ID. Prior successful runs are historical directories, not the current invocation. A decode, execution, schema, adaptation, or scoring failure records the case, mode, stage, diagnostic files, process exit status and timeout information; no selected mode publishes a score if any case/mode fails. A failed process may leave partial raw output inside its own failed run; it is never consumed or reused.

Before invoking tools the runner verifies the full manifest hash/inventory against the frozen lock and every selected WAV hash. Metadata records the lock/manifest hashes and complete selected input inventory (IDs, paths, sizes, hashes, durations/rates), binary path/size/hash, decoder path/hash/version, configuration/timeouts, UTC identity, platform/node/CPU/Python information, source revision/status/diff digest, and individual hashes of core/harness source and Cargo/toolchain/architecture files, including untracked files. This records the shared working tree, but cannot attest how a supplied binary was built; a frozen acceptance run must establish that association separately. No build, service, or external network access is performed by the runner. The raw-PCM CLI evaluates core inference; a separate backend upload run remains necessary to verify backend decoding and job plumbing.

Strict wire checks cover required fields, schema/engine/options identity, finite durations/times/tuning, span/coverage rules, pitch and spelling/name/cents ranges, harmony tagged unions/reasons/candidates/alternatives, bass MIDI/pitch-class consistency, bounded evidence, warnings, note/event/alternative limits, and feature duration/80 ms cell grid/12-bin nonnegative L2-normalized-or-zero chroma/MIDI/RMS plus JSON size limits. Unknown extra object fields are allowed as required by the architecture. Disabled explicit-mode note streams are contract failures; auto routing and cross-stream duplication are reported as diagnostics rather than hidden by the canonical union. No conflicting public Rust types were found at the time of this harness update.

Integration needs still to verify against implementation: CLI or callable entrypoint; accepted WAV/sample formats; time origin and frame/segment conventions; sample-rate/downmix behavior; pitch and chord vocabulary; unknown and confidence semantics; bass and polyphonic-set availability. Run every fixture through actual WAV decoding when the Rust path supports it. Capture decoder failures separately from detection failures. The TypeScript adapter currently decodes our known WAV layout itself and matches historical browser box-average resampling to 12 kHz; that baseline does not validate the browser decoder.

## Metrics

Scoring samples segment timelines every 20 ms, at interval centers. This gives approximately duration-weighted metrics; not event counts. Settled windows exclude the first 120 ms after the last strummed string and final 100 ms before damping. Overlapping chord events have no unique identity score. Single-note stable windows begin 130 ms after attack. The `mono_*`, `poly_*`, and unprefixed `note_*` metrics retain these settled exclusions; they do not validate attacks, releases, or overlap. Expected sustained notes include quiet decays; the high-register tail can become very quiet. Report the first 350 ms of each stable monophonic window separately (`mono_early_exact`) so a quiet tail cannot hide early pitch failures.

- `mono_exact`: exact octave-sensitive singleton MIDI-set accuracy on monophonic stable windows. Empty output and octave errors fail.
- `poly_midi_exact`: exact sounding MIDI-set equality on stable polyphonic windows. Unison duplicate strings are not individually scored.
- `poly_pc_exact`: exact pitch-class-set equality; intentionally ignores octaves.
- `note_precision`, `note_recall`, `note_f1`: micro counts of MIDI set intersections, extras, and omissions on stable polyphonic windows. Precision alone cannot disguise missing most voices.
- `overlap_midi_exact`, `overlap_pc_exact`, `overlap_note_precision/recall/f1`: separate timed-union note metrics wherever more than one reference chord event is active, including staggered attacks and releasing old voices. Identity/bass accuracy is excluded there; these diagnostics do not change the settled denominators or gates.
- Root, quality, and bass accuracies: reported separately. Root/quality use only unambiguous identities; bass uses all stable chords, including ambiguous ones. `chord_root_quality_bass` requires all three fields correct simultaneously.
- `compatible_identity_accuracy`: predicted root/quality matches a declared equivalent candidate. Report by intended quality, so large major/minor counts cannot hide failed extensions. `ambiguous_abstention` is descriptive; either abstaining or choosing a compatible name can be reasonable. A high abstention rate alone is not success.
- Negative false-positive rate: fraction of reference-empty frames emitting any notes or chord/bass identity, including silent lead/trail and dedicated negatives. Also report dedicated silence/noise/percussion groups separately: overall negative rate can be dominated by boundary smear.
- Transition boundary precision/recall/F1: only changes in predicted harmonic identity `(root, quality)` count. Note-set, octave, and bass changes alone never create harmonic boundaries. Null identity remains an observable unknown state, so internal chord/unknown/chord flicker counts. Reference times are the three nominal new-strum onsets (`event.start`), not individual string attacks or old-chord release ends. Match one-to-one within the unchanged 180 ms tolerance; ignore phrase entry/exit. Exact timed notes plus onset-aligned identities score 3 TP, 0 FP, 0 FN; the same notes with all-null harmony score 0 TP, 0 FP, 3 FN. Mean absolute matched error is reported alongside F1. This convention is a synthetic transition diagnostic, not a unique-identity score during overlap or a timing calibration for real recordings.
- Rust `streams` reports retain note provenance independently of the union. At every 20 ms timed-truth sample, including attacks/releases/overlap and negatives, auto assigns singleton truth to monophonic and multiple-pitch truth to polyphonic. Explicit monophonic expects refusal on multiple voices; explicit polyphonic expects all supported notes, including singletons. Each stream reports MIDI TP/FP/FN, precision/recall/F1 and exactness on its eligible voiced samples. Wrong-stream notes add FP to that stream and FN to the expected stream even when the union is perfect. `routing_accuracy` compares expected/observed channel activity, independently of pitch correctness; counts also expose wrong-stream frames, cross-stream duplicates, multi-pitch mono frames and explicit mono multi-voice refusal. These diagnostics use known timed voices rather than evidence cutoffs, are separate from settled metrics, and make no evidence-calibration claim.

Reports contain counts, per-file results, and groups by kind/intended quality. The mixed transition phrase is `transition:mixed`, not major-only accuracy. Null means no eligible observations, not 100% accuracy. Current aggregation is micro/duration-weighted; inspect each file and each quality before accepting an average. Single-note event precision/recall, velocity, duplicate-string assignment, continuous cents error, percussive onset matching, and resource/latency limits are not evaluated by this scorer yet.

## Proposed gates, to agree before running Rust holdout

These are engineering targets for this controlled synthetic corpus, not evidence of achieved quality and not release promises:

- Monophonic early-window accuracy at least 95%, sustained-window at least 90%; examine every failed note/register.
- Polyphonic pitch-class exact accuracy at least 85%; MIDI note F1 at least 85%, precision and recall each at least 80%. MIDI-set exact accuracy initially a reported diagnostic, with an 80% target once polyphonic note output is supported.
- Unambiguous root and quality each at least 90%, bass at least 85%; compatible identity at least 85%, with no intended-quality group below 70%. Require at least ten independent real takes per quality before treating per-quality real-world percentages as meaningful; current tiny groups do not support strong statistical claims.
- Dedicated silence/noise/percussion false-positive rate at most 1%; silent margins at most 10% after inspecting boundary tolerance effects.
- Internal boundary F1 at least 85% at 180 ms; always report matched timing error and false positives.

A missing output capability is unsupported, not a passing test. A supported subset may be released only with explicit scope and separate reporting; do not collapse extended chords to triads to improve scores. Revisit proposed thresholds on independent human-played development recordings before freezing a real-world holdout.

## Historical baseline findings for root/triage

All ten preexisting tests in the two relevant test files passed during original preparation; they were not rerun for this harness-only correction. On the independently generated **development** corpus, the historical baseline has sustained monophonic exact accuracy 43.32% (402/928 samples); early stable-window accuracy is 54.78% (149/272). These replace 42.03% and 54.04% after correcting nearest-frame support to adjacent-center midpoints; no detector, audio, or label changed. Open E2, F2, B2 and A2 still each have 0/17 early exact-note samples despite measurable waveform energy. Waveform autocorrelation confirms the generated single-note frequency, including detuning; these are not merely mistuned generators. Some upper-register tails are quiet, so distinguish early accuracy from sustained accuracy before diagnosing all failures as pitch errors.

On uniquely labeled chord windows, root accuracy is 80.10% and quality accuracy 50.47%. The implementation's only labels are 24 major/minor triads and N; seventh/suspension/extension/inversion support cannot be validated by the old test suite. It has one predominant MIDI field and no polyphonic set or bass field. The adapter emits only that observed MIDI as a singleton and leaves bass null; resulting polyphonic and bass failures are capability gaps, not estimates of an existing polyphonic algorithm.

Dedicated silence, noise, and percussion each have zero false positives in this small development set. Overall reference-empty false-positive rate is 48.14% (840/1,745 samples), replacing 49.86% after midpoint correction, concentrated in leading/trailing silent margins around played audio. Centered 4096-sample windows at 12 kHz and segment smoothing are plausible contributors, not a proven diagnosis. Investigate time-support mapping and post-decay state persistence independently before modifying implementation. With harmonic-only boundaries the three transitions all match with no false positives: boundary precision/recall/F1 are 100%, mean absolute matched error 24.67 ms. The former five extra note-state changes were not evidence of harmonic flicker. This says nothing about accurate note transcription: settled polyphonic MIDI/PC exactness remain 0%, settled note F1 is 9.53%, overlap MIDI/PC exactness is 0%, and overlap note recall/F1 are 2.13%/4.17% (7 TP, 0 FP, 322 FN across 45 overlap samples). Those failures reflect the baseline’s absent polyphonic capability. `baseline-summary.json` contains the corrected counts and groups.

Existing CCR fixtures are detector-extracted chroma/MIDI/RMS features, not source PCM, and reference comments say starts were refined to chroma flips. That is useful regression data but not independent audio-front-end ground truth. No clear reusable audio license/provenance was found for existing song-derived fixtures. They were not incorporated into this new corpus. The independent review remains unchanged. This harness correction changes no application code and provides no Rust acceptance evidence.

## Limits and real-recording follow-up

This synthetic harness work adds no real recordings and makes no human-recording accuracy claim. The separate real-audio evaluator owns `validation/real-audio/**` and `docs/rust-real-validation.md`; consult that report for its sources and results. The generated synthetic audio/labels are explicitly CC0-1.0, with provenance in the manifest and `validation/audio/LICENSE`.

Karplus–Strong is a useful string model, not a full guitar/acoustic-room simulator. This corpus has one synthesis family, mono audio, short sustained phrases, no fingers moving on real strings, no body/microphone response, no actual amplifier distortion, no alternate tuning, no stereo, and no other instruments or vocals. Capo variants are correlated with development shapes. It cannot establish full-song performance, robustness to real recordings, or all possible chord voicings. The overlap case is an intentionally controlled exception to physical damping, not a performance transcription.

Before product acceptance: collect original player-consented or clearly licensed recordings; retain source URL/author/license version and license file, original WAV/hash, instrument/tuning/capo/mic/room metadata, and permission scope. Have a player and a second listener review sounding notes, spelling alternatives, bass, and timing using listening plus waveform inspection, independent of detector output. Mark uncertain/unheard voices and ambiguous intervals rather than forcing labels. Separate takes/players/instruments between development and holdout. Include muted/choked strings, weak fundamentals, real strums/arpeggios, fret/handling noise, multiple dynamics, transitions, inversions and extended qualities. Review any public dataset's recording and annotation licenses individually before copying files. Freeze a complete Rust run with raw output and score reports; until then this work remains test preparation and historical baseline assessment.
