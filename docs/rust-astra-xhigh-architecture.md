## Overflow, end to end (Q1)

- **Core/native CLI:** `segments.rs:135,204` abort on the first exceeded stream/harmony cap. `lib.rs:328–335` limits the serialized result to 1 MiB minus 2,048 bytes reserved for the server envelope. There is no feature-only output. `src/bin/analyze-pcm.rs:69–84` maps limits to exit 3 before atomic result writing. Invalid input and cancellation remain distinct failures.
- **Rust jobs:** `jobs.rs:488` maps core limits to `RESULT_TOO_COMPLEX`. It independently checks event/frame counts and final envelope/features at `:495–514` (1 MiB result, 8 MiB features). Artifacts are stored only after all checks (`:524`); failure records status/error (`:307`). The scheduler clears unsuccessful-job files (`:360`), including decoded playback. `api.rs:232,250,316` denies result, features **and audio** unless succeeded. Merely attaching features to a Rust error will not expose them or preserve playback.
- **Node gateway:** it validates routes and byte limits, **not the analysis JSON schema** (`server/analysisApi.ts:77–114,251–303`). Overlarge advertised bodies become 503; streaming overrun destroys the response. Result/features caps are 1/8 MiB, other JSON 16 KiB. Recovery data cannot be stuffed into an ordinary job/error response.
- **Browser jobs:** `analysisClient.ts:239–247` throws immediately on failed status, never fetching artifacts. Artifact fetching is all-or-nothing via `Promise.all` (`:269`); parse/association/network failure also rejects the operation. Finally DELETE runs (`:296`). `AudioAnalysisPanel.tsx:106` displays an error without saving a new result; a previous result can remain. Existing saved songs are not erased by that failed request.
- **WASM:** `crates/fretbloom-wasm/src/lib.rs:62–68` throws a generic JSON-string `LIMIT_EXCEEDED`; no partial output. `analysis.worker.ts:80–109` turns it into an error reply. `ingest.worker.ts:401` kills that engine and throws. Live pump failures stop capture and retain previous valid ledger/audio (`:741–758`); refinement accumulates results privately and only replaces the stopped analysis after every segment validates (`:923–961`). UI explicitly retains previous results on refinement failure (`LiveListen.tsx:481–488`).
- **Live caps are not just whole-file caps.** A 2.56 s core call has at most 128 20-ms frames (`live/protocol.ts:170`; core `config.rs:2`). Six raw fitted voices (`polyphony.rs:105`) permit at most nine median-filtered memberships per interior frame (`segments.rs:47–58`): at most 1,152 note memberships and 128 harmony spans. Thus the core count caps cannot fire on this normal window. Its bounded current event representation also has ample room under the core JSON cap; this is not a new measured worst-case serialization benchmark. Whole-file/refine calls can overflow. Separately, the **accumulated live ledger** enforces 4,000/3,000 (`rollingTimeline.ts:218`), and the session parser enforces combined counts across segments plus 2 MiB metadata (`live/validation.ts:162,239`). Those can fail during live capture even when every window succeeds; O2 does not automatically solve them.
- **Saved IndexedDB sessions:** `listeningSessions.ts:70–119` reparses local analysis, identity, audio length and 2 MiB metadata. Old complete v1 records remain readable across engine changes; refine requires explicit engine-change consent (`ingest.worker.ts:911`). Failed refinement does not persist a replacement. Songbook saves use a separate `SavedAudioAnalysis`/songbook path, not this listening-session database. Both need consideration if partial output becomes persistable.

### Q1: compare the two shapes

**(a) A required, discriminated outcome is safer for O2's complete feature set.** Preserve the existing complete `AnalysisResult` inside a `complete` outcome; define an explicitly versioned `alignment_only` outcome with source/PCM/options/engine/duration/tuning/warnings and a typed reason (`note_limit`, `harmony_limit`, `result_bytes`). Do not encode unavailable events as empty successful arrays. V1 parsers allow empty harmony and discard unrecognized fields (`analysisV1.ts:375,404`), so an optional flag can silently become a successful empty transcription in an old reader. A negotiated/new envelope version must make older readers reject partial outcomes. Existing v1 complete records must remain readable.

**(b) Error-with-features is smaller only if recovery is transient and server-only.** It leaves `AnalysisResult` and old saved records untouched and preserves CLI/scorer failure naturally. But the actual jobs delete failure artifacts; routes reject them; the browser throws before fetching; WASM error parsers discard fields; refine commits only complete results. To deliver bounded features/audio, (b) needs a separate recoverable-artifact contract, retention exception, associated metadata and client state anyway. To save it, it also needs a new session variant. It is not a cheap cross-stack exception. Prefer (b) only for a deliberately narrower unsaved fallback, with unchanged live/refine behavior—not as an implementation shortcut for the proposed O2.

For full O2, prefer (a)'s explicit outcome, but **defer implementation now**. A recovered artifact can succeed operationally while its event evaluation remains failed/unavailable; do not overload one status with both meanings. Keep old evaluator results immutable. A new evaluator adapter must record incomplete status and no musical score for these outputs. It must never turn the old exit-3 cases into empty passing transcriptions.

The three cited 552-second recordings are outside the 300-second browser limit and are note exercises, not demonstrated sheet-alignment successes. They justify server graceful recovery research, not an immediate promise that “sheet sync still works”. Proposed UI: “Recording analysis exceeded its output limit. Basic sheet timing may still be available; detailed notes/chords are unavailable.” Rich targets must still refuse unsupported timing.
