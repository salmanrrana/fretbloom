# Independent architecture review: cancellation repair

2026-10-31. Reviewer: Astra, xhigh. Scope: the lead plan, active worker/bridge/core/build sources, frozen speedup tests, and supplied diagnostics. No product code changed. Reviewer writes are this document and `target/cancel-repair-review/**`.

## Decision

**Root cause confirmed for the pinned Chromium 143.0.7499.4.** Blink schedules forcible termination after two seconds while its ordinary shutdown needs the occupied worker thread to run a task. This explains the root's continuing CPU, independently of CDP, nesting, or the numerical optimization. It is an implementation observation, not a browser-independent two-second upper bound.

**Conditional GO for implementing JSPI; NO-GO for declaring the proposed plan a complete portable repair.** JSPI is the smallest promising repair for browsers providing it, and independent synthetic measurements support it. Product ABI integration, complete non-yielding intervals, throughput, memory, and preserved-session behavior remain unproved. The synchronous fallback knowingly fails on affected Chromium without JSPI. Reporting that failure honestly does not satisfy the unchanged ≤250 ms contract. Resolve the supported-browser coverage before release; do not silently lower the gate or disable an existing public capability without an explicit product decision.

The key required changes to the plan are:

1. Specify the real multivalue/externref ABI and reproducible import injection; do not propose a retptr shim for this artifact.
2. Treat fallback coverage as an unresolved release condition, not an accepted exception.
3. Measure the entire request, including JS preprocessing/postprocessing and ingestion restore decoding; predicate-to-predicate gaps alone are insufficient.
4. Define retry as a fresh generation restored from the retained, hash-verified PCM, preserving the once-per-generation rule.
5. Bump the internal bridge version for the new required import/initialization contract, while preserving numerical and saved-session identities if parity passes.
6. Make the independent tester's CPU evidence robust to census timing, missing busy threads, and cancellation near completion.

The synchronous testing path is at 315. The copy's full SHA-256 is `b38b9716acd6e98f8f35c1c3df7d3ca1fab217f087a54915a897e76fd8dc46a3`, matching the lead's prefix/suffix.

This confirms the proposed mechanism. Qualify “only posts a task”: termination also changes state and disposes inspector work. Qualify “≤2 seconds”: the fallback runs on a parent task runner and can be postponed during debugger work; two seconds is the configured delay, not a universal maximum.

I inspected `target/cancel-repair-lead/diag/{synthetic,jspi,other-browsers-1,other-browsers-2}.json`, its harness and page/worker sources. Those support the claimed JS/WASM, ownership and launcher comparisons. Empty Firefox `threads` arrays and WebKit `no-marks` are inconclusive, not successful tests. The synthetic loop proves a scheduling mechanism, not the Rust product bridge or every cancellation phase.

## Minimal integration with wasm-bindgen 0.2.100

The shipped JS is unusually helpful: it already uses multivalue returns. `fretbloom_wasm_bg.wasm.d.ts` declares:

- `analyze_pcm_json(ptr, len, rate, optionsPtr, optionsLen) -> [number, number, number, number]`;
- `engine_info_json() -> [number, number]`;
- an externref table and deallocator.

The generated analyze wrapper copies PCM and UTF-8 options, calls the raw export synchronously, examines `[ptr, len, errorIndex, isError]`, takes/deallocates an error externref, decodes the returned string and frees it. **There is no JS-managed retptr or `__wbindgen_add_to_stack_pointer` in this artifact.** Rust still has linear-memory stack/allocator state; JSPI suspension does not authorize re-entry.

The smallest reasonable shape is a raw host import plus a narrow, reproducibly generated async adapter around this existing export:

1. In the WASM bridge only, import `fretbloom_host.poll() -> i32` using a raw `extern "C"` declaration with `#[link(wasm_import_module = "fretbloom_host")]`. Pass a zero-capture closure calling it to the existing `cancelled` argument. Keep native bridge tests linkable with a target-specific non-WASM implementation. Leave the analysis crate's recognition arithmetic alone.
2. Inject the **actual `WebAssembly.Suspending` object** into the instance's import map. The host function returns numeric zero synchronously on most calls and a `Promise<number>` resolving to zero when a task yield is due. Keep the ordinary synchronous host import as `() => 0` for synchronous tools and explicitly tested fallback instances. No posted-cancel flag is needed for this repair: the owner still terminates the worker. Omit the optional clean-cancellation protocol unless evidence requires it.
3. Use `WebAssembly.promising(rawExports.analyze_pcm_json)`, then `await` its four-value result **inside** an async version of the generated allocation/decode/error/free wrapper. Do not pass the exported JS wrapper to `promising`, merely add `await` to the synchronous wrapper's caller, or insert an intervening JS callback that must itself suspend. All three miss the required boundary.
4. Retain synchronous entry points for existing parity/build tooling with a non-suspending import. A worker initialized with a suspending import must use the async analysis adapter exclusively. Preserve the generated wbg error/string/externref initialization helpers, including `__wbindgen_start()`, rather than inventing another loader.

There is a concrete missing build step in the lead plan: the pinned generator automatically emits `import * as __wbg_starN from 'fretbloom_host'` and assigns that namespace to the extra import module. See installed `wasm-bindgen-cli-support-0.2.100/src/js/mod.rs`, `gen_init`, lines 875–898. Current `init({module_or_path})` has no host-import argument. Adding the Rust declaration and changing the worker alone will not wire it up.

My recommendation is one small guarded post-generation adapter in `scripts/wasm-build.mjs` (or a source-hashed helper): replace that exact raw module wiring with an explicit init option/default, and generate the async analysis wrapper/declarations using the pinned wrapper's ABI. Check exact expected shapes/counts and fail the build on drift. Update both init paths or explicitly reject unsupported combinations. Do not monkeypatch global WebAssembly methods, mutate non-writable instance exports, or hand-edit active generated assets. Keeping allocation/error handling in the generated wrapper avoids maintaining a second complete bridge. A hand-written adapter is also viable if its complete ownership rules are reviewed and source-hashed; it is not automatically simpler.

Type the async raw call from the generated `InitOutput['analyze_pcm_json']` parameters/return type. Describe JSPI's optional API narrowly where TypeScript lacks it; use `unknown` at untrusted boundaries, with no `any` escape hatch or scattered casts. Test a real `i32` import: the synthetic import has a void return and cannot validate the product's boolean conversion. Resolve the yield promise with `0`, not the `MessageEvent` that the lead's diagnostic callback receives.

Input allocations and return/error allocations must follow the generated ABI's existing ownership, not a guessed C ABI. Never release inputs before the awaited call settles or double-free memory already owned by the bindgen adapter. Only decode/free a valid success return; preserve error-index extraction and deallocation. On traps or rejected suspension, discard the instance through the existing engine-failure path. Test success, invalid input, thrown Rust JSON, repeated calls and a trap/rejection path.

A new raw C-ABI analysis export would require new length/result/error/lifetime conventions and more unsafe Rust. It does not improve cancellation and is larger than adapting this existing multivalue export. Upgrading wasm-bindgen for newer JSPI support would be a separate toolchain migration; current upstream support does not make the pinned 0.2.100 glue async-aware.

## Scheduling, re-entry, identity and saved sessions

Use a **task** yield, such as MessageChannel; `Promise.resolve()` or a microtask alone does not let the worker process shutdown tasks. Return a promise only when the roughly 50 ms budget expires; an `async` import that always returns a promise would suspend at every predicate call. Measure elapsed time with `performance.now()`, resetting the budget for each analysis and after a resumed yield. Use a single reusable channel or close both ports after every one-shot tick. The synthetic creates channels without closing them: do not copy that resource behavior into production.

Both live and refinement use this same worker/export. The ingestion worker currently serializes normal requests using `waiter`, `running` and `refining`, but the analysis worker's async `onmessage` is not a mutex. Add an explicit initializing/ready/busy guard before any allocation or WASM call. Hold it through awaited analysis, decoding/freeing and reply construction, releasing it in `finally`. No second analysis, repeated init, `engine_info_json`, allocation or other export may run while analysis is suspended. Reject invalid concurrent requests; do not introduce an unbounded queue. Read/cache engine info once after initialization. Keep each request's key/id stable across the await.

The existing ownership model is sound for this repair: `killEngine` detaches handlers, terminates, increments engine generation, rejects the waiter, clears timers and resets engine readiness. Keep it. The ingestion deadline already runs outside the DSP worker. JSPI must not reset the **120 s total** refinement deadline for each segment or yield. Keep the live **5 s** timeout and its `ANALYSIS_TOO_SLOW` behavior, the facade's 121 s fallback, and deadline/late-result guards. Test cancellation while booting, while actively computing, while suspended and close to completion. A normal `stop()` drains accepted live work; do not relabel that as a cancel to make a test pass. Live abort/dispose and the live watchdog are distinct cases.

`refineUsed` is set before work and intentionally never reset. Architecture line 303 says once per generation. Thus “retry succeeds” means export retained PCM after cancellation, verify its digest, restore the unchanged snapshot plus PCM under a fresh generation, then refine. Do not silently reset `refineUsed` as part of this cancellation patch. Restore itself does not perform DSP; distinguish cancel during Blob/hash/decode restore from cancel during the later engine-upgrade refinement. If restore is aborted, its original saved Blob/snapshot must remain usable even though the newly created ingestion worker is terminated.

Preserve `LocalAnalysis` schema, options, segment offsets/gaps, unknown/no-chord/bass/null semantics, both note streams, old result visibility and atomic replacement only after full validation. Check near-completion races explicitly: rejecting the main promise alone does not prove a queued `refined` event cannot still be adopted.

**Use bridgeVersion 2** for the new import/initialization/async bridge contract; update the Rust info, worker check, manifest creation, verifier and relevant fixtures together. Keep schemaVersion 1 and `rust-dsp-3.1` only after exact result-and-feature output parity. Changing the bridge must not force old sessions through a numerical engine-upgrade flow. Source hashes and WASM artifact hashes must change normally; “WASM byte parity” here means output bytes, not equal old/new `.wasm` binaries. Run the guarded staged build/publish and clean regeneration check; include every adapter/helper in source identity and generated JS/declarations in artifact hashing.

Compare the native executable before/after cancellation changes against the **same chosen speedup candidate and pinned build environment**. It should be identical when only the WASM bridge/JS and test-only code change. Do not compare a newly adopted optimized native binary to the old unoptimized active binary and attribute that difference to cancellation. If measured gaps require changes in shared core code, an unchanged native hash becomes a new proof obligation, not an assumption. Prefer bridge-only fixes first; report any unavoidable hash conflict to the lead rather than hiding it.

## Non-yielding gaps the builder must measure

Existing predicate sites are frequent, but “throughout the engine” is not a latency bound. On 300 s there are 7.2M samples and about 15,000 analysis frames. None of the following is established to exceed 150 ms on the target machine, but none is ruled out by the code or synthetic proof:

- **Before the first poll:** generated `Float32Array.set` copies 28.8 MB into WASM; the bridge's `validate` does a full `mono.iter().any` finite scan without a predicate. Options parsing and allocation also occur before `analyze` reaches its first check.
- **Per-frame bounded work:** FFT setup/planning, `SpectralAnalyzer::compute` (including peak-neighborhood sorts and logarithms), `Yin::estimate`, and `current_support`/its sample-band measurements have no internal predicate. `measure` polls per anchor/iteration, but its initial `compute` does not. `polyphony::fit` polls per MIDI and fit iteration, with peak/candidate inner loops between checks; `VoiceEvidence::observe` has candidate-level checks, not one per inner operation. Measure dense/high-peak fixtures as well as ordinary music.
- **`segments::finish`:** deep cloning the complete frame vector precedes its first check. The note-stream extraction checks once per MIDI and then scans **all frames** before checking again. Sorting up to 4,000 notes per stream and the tentative-harmony confirmation loop (up to 3,000 harmony spans) have no internal checks. Median smoothing and pitch-confirmation loops do check per frame; feature construction checks per four-frame group. Cleanup/destruction of frame vectors also costs time.
- **After the last poll:** core result-size JSON serialization, output construction/cleanup, bridge serialization of result plus features, WASM-to-JS UTF-8 decoding, `JSON.parse`, `parseOutput`, and reply cloning have no JSPI checks. Include success and error tails, not just the DSP loop.
- **Outside DSP entirely:** ingestion `restore` decodes a full little-endian Blob in a synchronous outer loop over CHUNK, with finite validation and `Recording.append` including per-sample ring writes. Having a chunk loop does not yield. `Recording.copy` before posting refinement and export's full-sample encoding also run without event-loop turns. JSPI cannot fix those JS intervals. If restore decoding exceeds the budget, insert bounded task yields there, preserving atomic restore state and cancellation/generation checks; do not rewrite recognition.

Instrument a diagnostic copy of the **real built product** to record entry-to-first-poll, maximum poll-to-poll interval, time between actual task yields/resumptions, last-poll-to-reply/throw, request copy/validation, restore decode, and phase boundaries. Record check/yield counts and p50/p95/max timings; do not emit one console/network message for every check. Benchmark 30 s and valid 300 s polyphonic recordings, dense/sideband inputs, silence, all modes, and bounded/high-output cases. Include the exact optimization candidate that will ship.

Use roughly 150 ms as an engineering ceiling for unchecked work, with roughly 50 ms yield scheduling and measured delivery/shutdown margin inside 250 ms. It is not a substitute for the real handler-to-stop measurement: independent bounds can add, and host scheduling can vary. Report actual worst gaps and cancellation phase sweeps on named hardware. If a gap fails, add only the necessary bounded polls/yields, preserving arithmetic/order, and rerun parity. Import plus `performance.now()` costs can be significant: the pitch-confirmation loop alone makes roughly a million checks on a full input. Do not infer negligible overhead from the infinite-loop synthetic.

## Browser coverage and alternatives

Feature-detect both JSPI APIs in the worker, and exercise suspension with the generated product module. Chromium 137 is the documented default-support starting point; old/disabled-feature Chromium must be treated as an actual failing branch, not assumed ≤250 ms. [V8's API explanation](https://v8.dev/blog/jspi-newapi) describes returning a non-promise without suspension; [V8's JSPI overview](https://v8.dev/blog/jspi) documents shipping support. The [WebAssembly proposal](https://github.com/WebAssembly/js-promise-integration/blob/main/proposals/js-promise-integration/Overview.md) describes the raw promising/suspending boundary.

Do not freeze “Safari has no JSPI” into the plan. WebKit documents JSPI in [Safari 27 beta](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/). That says nothing about pinned `webkit-2359`, older Safari, or this product's termination timing. Current public sources also differ on Firefox release numbering; record the actual installed browser version and detected feature state. Independently test Firefox's forced synchronous branch even if its JSPI branch exists. The provided WebKit load failure is an infrastructure blocker, not browser evidence.

For a release supporting non-JSPI engines, either demonstrate that their ordinary worker termination meets the same gate, supply a passing alternative, or obtain an explicit supported-browser scope decision. A label warning of two seconds does not make the current contract pass. Do not silently introduce browser sniffing or narrow availability under this review's authority.

Alternatives considered:

- **SAB/Atomics flag:** small poll mechanism on an already isolated site, and avoids async stack integration. Here it adds COOP/COEP/deployment requirements, with potential YouTube iframe and cross-origin resource consequences. It still needs bounded check gaps and a cooperative flag set before/alongside terminate. Not the smallest repair for the present hosting contract; requires an actual embedding/hosting compatibility test, not a blanket assertion that embeds can or cannot work.
- **Binaryen Asyncify:** a credible non-JSPI fallback, instrumenting WASM so a host task can unwind/resume it. Broader toolchain changes, stack/memory cost and import/export wiring need the same product/parity testing. It may beat JSPI plus a failing fallback if broad older-browser support is mandatory. Do a bounded feasibility spike only if coverage requires it.
- **Explicit resumable Rust state:** most controllable portable scheduling, but retaining all intermediate state across every analysis/segmentation phase is a substantially larger change. Next option if JSPI/Asyncify cannot satisfy support and performance requirements.
- Moving worker ownership, terminating the parent, a bare cancel message, and an async JS wrapper around the sync export do not interrupt occupied Chromium code. Independent analysis windows alter the algorithm and remain prohibited. Sync-XHR/service-worker/OPFS cancellation channels add complexity without a justified advantage.

None beats JSPI on minimal change for the tested modern Chromium; that does not establish JSPI alone as a complete cross-browser solution.

## Remaining blockers

No real-product JSPI build exists in the reviewed evidence. Product gap, throughput, memory, ABI, retry and race gates are therefore outstanding. The known failing non-JSPI Chromium branch has no approved compatibility solution. Safari/WebKit product termination remains untested. Shared-core polling changes, if needed, may conflict with the required unchanged native hash. These are implementation/release conditions, not reasons to reject a narrow JSPI prototype.
