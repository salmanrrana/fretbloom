## Finding 1 — finite ownership graph; missing joins, not a demonstrated overflow

All product source line references below are relative to `target/cancel-control-repair/frozen/source/`. Harness references are relative to this checkout's `validation/cancel-repaired-browser/`, unless explicitly prefixed otherwise.

### Actual source graph and lifetimes

1. **Capture and canonical storage.** `capture.worklet.js:61–62` creates eight buffers, each at most 16,384 bytes. Full blocks transfer; partial Stop flush uses a slice (`139–161`), with recycling at `95–100`. Ingestion receives views, downmixes and resamples (`ingest.worker.ts:588–633`). `Recording` owns chunk backings plus its 983,040-byte ring (`54–107`); chunks never exceed 7,200,000 samples together. The pending analysis job is extent metadata, not another PCM window (`708–721`). Channel-decision copies, downmix output and resampler old/new/output arrays are real capture temporaries (`590`, `618`; `resampler.ts:19–24,49,78–82`), not new five-minute copies. Stop closes the segment and clears the resampler/decision roots (`ingest.worker.ts:658–683`). A capture bound must include those small scratch maxima, but they need not be carried through every stopped Save/play phase.
2. **Refinement.** `Recording.copy` allocates one segment-sized input (`79–96`); segments are analyzed serially under `heavy` (`906–962`). Ingest posts its backing with the transfer list (`367–399`); `analysis.worker.ts:101` makes a view, not a second JS copy. Portable glue copies that input into WASM linear memory (`portable/fretbloom_wasm.js:68–72,155–174`). That WASM copy and saved stack belong to the separate linear-memory accounting, once. The worker's handler keeps its JS input across the awaited analysis, then returns after reply/finally (`analysis.worker.ts:101–116,153–155`). There is no product field caching past PCM requests. A queued or terminated old worker is a different lifetime problem from an already completed local temporary awaiting GC.
3. **Export.** Ingest's heavy guard excludes refinement and export from one another. Export creates one full f32 array, a 32-byte digest, then an immutable Blob (`970–998`). The full array and Blob coexist at construction. The RPC reply carries the Blob (`1121`); ingestion does not cache it in a class field. The facade caches the returned Blob in `exported` (`runtime.ts:471–497`). UI `getPcm` stores that exact returned object and generation (`LiveListen.tsx:503–518`). This main-realm overlap is source-proven; it does not establish native backing identity for every cross-realm clone.
4. **Restore.** The facade posts the caller's Blob, awaits verified ingestion restore, then caches the **original caller reference**, not a returned Blob (`runtime.ts:412–441`). Thus, in the memory harness, `before.pcm` returned by the cached `exportPcm` after restore refers to the same main-realm `pcm`; it is not another Blob construction. Ingestion performs one full `arrayBuffer()` read and hash, then copies little-endian samples through at most 65,536-byte scratch chunks into canonical recording (`ingest.worker.ts:1000–1048`). The read, growing canonical chunks, caller PCM and final scratch can coexist. The source's `operationBytes` reservation is not an independent allocation measurement.
5. **Save verification.** `LiveListen.tsx:543–555` calls `player.release()` before obtaining/verifying PCM. Release clears the WAV ref, audio source and URLs (`LocalSessionPlayer.tsx:119–139`). `pcmOperations.ts:1–28` serializes WAV preparation and verification and admits at most eight operations; queued calls do not yet allocate a WAV/full read. `pcmVerification.ts:20–39,59–84` reserves read+digest, posts a Blob to a dedicated worker, and terminates on every outcome. `pcmIntegrity.ts:15–29` owns one full read and digest, with DataView as an alias. Save verifies before opening its atomic write transaction (`listeningSessions.ts:209–224`). **Queue completion and zero reservation do not establish that an aborted/timed-out worker has exited.** No cancellation-overlap memory proof for this verification path is in the reviewed records.
6. **WAV/playback.** `LocalSessionPlayer.tsx:12–69` allocates one WAV array, reads PCM in at most 262,144-byte chunks, and constructs a distinct WAV Blob while the array is still owned. Its last read DataView is scoped inside the loop; it is not a second permanent full PCM. The WAV ref, playback URL and download URL can all retain the **same WAV Blob**, rather than three WAV payloads (`72–84,115–139,181–197`). UI releases playback before refinement as well (`LiveListen.tsx:422–423`). The serial queue does not by itself serialize ingestion refinement/restore; the UI's disabled/busy flow and release ordering matter.

### Useful arithmetic, with explicit conditions

Let P=28,800,000 (maximum PCM), R=983,040 (ring), Q=131,072 (existing conservative transport reserve), E=R+Q=1,114,112, W=14,400,044 (WAV). [bound-arithmetic.json](../target/cancel-audio-ownership-review/bound-arithmetic.json) retains exact integer arithmetic. For a stopped single canonical recording, one joined PCM Blob, and no old still-owned input/read:

| Operation | Conservative source envelope, bytes |
|---|---:|
| Refine with retained PCM Blob: canonical+transfer+Blob+E | 87,514,112 |
| First capture export: canonical+export array+new Blob+E+digest | 87,514,144 |
| Save verification: canonical+Blob+read+E+digest | 87,514,144 |
| Restore: Blob+full read+canonical+E+scratch+digest | 87,579,680 |
| WAV chunk read: canonical+Blob+WAV array+E+read chunk | 73,376,300 |
| WAV construction: canonical+Blob+two WAV payloads+E | 87,514,200 |

These are conditional envelopes, **not a new measured PASS**. The old R2 value's reappearance is arithmetic, not permission to transfer its acceptance. A legitimate full extra P would consume more than the remaining headroom: four distinct simultaneous P-sized payloads alone total 115,200,000 > 100,663,296. No reviewed record establishes that four such **distinct application payloads actually coexist** on the real UI path. An unresolved Blob clone is neither a proven alias nor a proven extra copy.

Serialization and source extents can close most of this without logging every allocation. One must independently establish the full-size value's identity, operation start/end ownership, and the few old-owner intervals. Local code that returns with no retained buffer root ends application ownership; native allocator reclamation and GC need not be synchronous. Worker termination is different: its running handler can still own an input until the worker actually exits. Native browser/WebCrypto/IDB/AudioContext internals remain outside this cap; no physical Blob-storage certificate is requested.

Stop/end-barrier/refine/storage/playback occur later and have not been reached by any retained checkpoint. Worklet initialization and PCM request exclude a stall solely before initialization, but do not establish audio-clock progress or a correctly acknowledged ingestion attach.

### Harness versus real UI

`identity/.../blank.html:6–7` automatically calls `run()` from module startup after a fetch; the runner only navigates (`browser-lifecycle.mjs:113`). It never clicks Start. The harness constructs an AudioContext, awaits engine/worklet/PCM setup, and only then calls `resume()`.

The real UI renders `onClick={start}` (`LiveListen.tsx:809`); `start` calls `LiveCapture.start` without awaiting preparation (`301–334`). Capture invokes the picker/getUserMedia, constructs its context and calls **resume before its first await** (`capture.ts:76–117`), then loads the worklet and connects the source. It uses a MediaStream source, rather than the harness's AudioBufferSource and extra relay channels. These are meaningful differences in activation and initialization order.

Chromium explicitly receives `--autoplay-policy=no-user-gesture-required`. Firefox's runner explicitly sets `media.autoplay.default:0` and `media.autoplay.blocking_policy:0`; WPE receives neither those preferences nor the Chromium flag (`browser-lifecycle.mjs:94–106`). These launch settings do not observe whether a given resume actually resolves. **Autoplay is a hypothesis, not an established cause**, particularly for Firefox with those preferences. WPE's reported Safari-looking user agent does not turn this Linux WPE run into Safari coverage.

Concrete classification: **harness diagnostic/representativeness gap established; precise runtime cause missing; no product defect established.** The fixed timeout label is a definite small harness reporting bug. Firefox CPU-attribution ambiguity is a separate scope and supplies no proof of broken cancellation. The already corrected channel oracle/partial-tail failures happen later than the last proven point here; they cannot explain this stall from these records.
